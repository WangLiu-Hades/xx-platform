## 补充记录：2026-10-25 迁移漂移修复（DEV-01，V3 增量）

本节追加于 PD-2026-10-18.v1 之后的实现阶段，只记录后端迁移链的一次真实修复；不改变上文暂定设计与甲方待确认状态。

### 现象

`apps/api` 的 `mvn -o -B test` 出现 2 条红灯，均在 `MigrationBaselineTests`：

- `baselineMigrationMatchesContractSchema:82`：V1 与 `contracts/database/schema.sql` 不再逐字节一致；
- `contractSchemaHashIsUnchanged:95`：期望 `7d3534b5…`，实际 `05a894a7…`。

### 根因（已用 git 举证，与任何"草案撤回"无关）

契约提交 `b2f6374`（2026-10-18 14:27，`schema.sql` +70/−13）把审批聚合写进了契约，但**没有提交对应的 Flyway 增量**；`V1__baseline_design_2.sql` 是 163 表的逐字节快照且已冻结。因此从 2026-10-18 起，空库执行 V1+V2 得到 163 表，而契约是 165 表——迁移链与契约之间的漂移，与 `contracts/database/migrations/drafts/` 的草案试验无关（该目录撤回后为空，`git status` 无 DDL 残留）。

差异清单（V1 相对契约缺失）：表 2（`operation.action_approval`、`audit.action_approval_decision`）、索引 3（`ix_action_approval_requester`、`ix_action_approval_pending`、`uq_decrypt_request_approval`）、触发器 1（`tr_action_approval_decision_append_only`）、列 4（`decryption_request.approval_id`、`decryption_result_grant.result_file_id` 可空化 / `approval_id` / `consumed_at`）、具名约束 1（`ck_decrypt_controlled_no_file`）、策略文案 12 行（`core.feature_config`）。无多余表、无列类型差异。

### 规矩（评审按此驳回）

1. 一次提交内同时包含：`schema.sql`（含数据字典、`api-storage-map`）+ `V<n>__*.sql` 增量 + `EXPECTED_CONTRACT_SHA256` 新值 + 守卫用例期望对象更新；缺增量即为漂移提交。
2. 不修改已发布的 `V1…Vn`，只追加 `V(n+1)`；改老迁移会让已部署库 `checksum mismatch` 起不来。
3. 增量不写 `IF NOT EXISTS`；手工跑过 `contracts/database/migrations/PD_20261018_approval.sql` 的库，须先确认 `SELECT to_regclass('operation.action_approval')` 为空。
