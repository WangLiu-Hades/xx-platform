## 补充记录：2026-10-25 迁移漂移修复（DEV-01，V3 增量）

本节追加于 PD-2026-10-18.v1 之后的实现阶段，只记录后端迁移链的一次真实修复；不改变上文暂定设计与甲方待确认状态。

### 现象

`apps/api` 的 `mvn -o -B test` 出现 2 条红灯，均在 `MigrationBaselineTests`：

- `baselineMigrationMatchesContractSchema:82`：V1 与 `contracts/database/schema.sql` 不再逐字节一致；
- `contractSchemaHashIsUnchanged:95`：期望 `7d3534b5…`，实际 `05a894a7…`。

### 根因（已用 git 举证，与任何"草案撤回"无关）

契约提交 `b2f6374`（2026-10-18 14:27，`schema.sql` +70/−13）把审批聚合写进了契约，但**没有提交对应的 Flyway 增量**；`V1__baseline_design_2.sql` 是 163 表的逐字节快照且已冻结。因此从 2026-10-18 起，空库执行 V1+V2 得到 163 表，而契约是 165 表——迁移链与契约之间的漂移，与 `contracts/database/migrations/drafts/` 的草案试验无关（该目录撤回后为空，`git status` 无 DDL 残留）。

差异清单（V1 相对契约缺失）：表 2（`operation.action_approval`、`audit.action_approval_decision`）、索引 3（`ix_action_approval_requester`、`ix_action_approval_pending`、`uq_decrypt_request_approval`）、触发器 1（`tr_action_approval_decision_append_only`）、列 4（`decryption_request.approval_id`、`decryption_result_grant.result_file_id` 可空化 / `approval_id` / `consumed_at`）、具名约束 1（`ck_decrypt_controlled_no_file`）、策略文案 12 行（`core.feature_config`）。无多余表、无列类型差异。

### 规矩（评审按此驳回）

1. 一次提交内同时包含：`schema.sql`（含数据字典、`api-storage-map`）+ `V<n>__*.sql` 增量 + `EXPECTED_CONTRACT_SHA256` 新值 + 守卫用例期望对象更新；缺增量即为漂移提交。

## 补充记录：2026-10-26 迁移校验脚本加固（DEV-01，评审 A05）

评审 `PR审查报告_20261026.md` 的 A05：`verify-migration-parity.ps1` 用两个**固定库名** `parity_mig` / `parity_ref`，开场一条 `DROP DATABASE IF EXISTS` 再重建，结束的 `finally` 也按固定名删——只要同一实例上有人（或另一次并发运行）也叫这两个名字，脚本就会把人家的库删掉。校验脚本自身不该具备删库能力。

### 改法

- 库名改为**每次运行唯一**：`parity_<pid>_<MMddHHmmss>_mig` / `…_ref`，工作目录 `apps/api/target/pg-parity/<pid>_<MMddHHmmss>` 同源，并发运行互不干扰；`-RunTag <1-24 位 a-z0-9_>` 可把 tag 固定下来（仅用于自测与复现，名字仍带 `parity_` 前缀）。
- 建库前先查 `pg_database`：**名字已存在就拒绝运行、退出码 2**，不做任何 DROP。
- 用 `$createdDbs` 记录本次真正建成的库，`finally` 只删这个清单里的条目 → 中途失败（例如第 2 个库没建成、迁移报错）也只清理自己建的那几个，别人的库与半成品一律不动。
- 保留原有的 0 一致 / 1 漂移 / 2 环境问题退出码语义，以及 `-Keep` 保留工作目录。

### 证据（本机 PG 16.15，端口 55434）

| 场景 | 结果 |
| --- | --- |
| 手工先建 `parity_probe_mig`，再跑 `-RunTag probe` | 退出码 2，报 `refusing to run: database 'parity_probe_mig' already exists`；运行后该库**仍在** |
| 删掉冲突库后跑 `-RunTag probe` | `PASS  structure is identical: 3033 fingerprints match (165 tables)`，退出码 0，`cleaned up parity_probe_mig, parity_probe_ref`，实例上 `parity%` 库计数 0 |
| 临时注入坏迁移 `V9__zzz_selftest_only.sql`（语法错误）后跑 `-RunTag partialtest` | 退出码 2、报 `migration failed`，仍输出 `cleaned up parity_partialtest_mig, parity_partialtest_ref`，`parity%` 计数 0；坏文件已删除 |

## 补充记录：2026-10-26 会话与查询窗口参数对齐（DEV-01，评审 A04）

评审 `PR审查报告_20261026.md` 的 A04：`docs/project-governance/provisional-policy.json` 已按 PD-2026-10-19.v1 把空闲超时定为 900 秒（15 分钟）、绝对超时 28800 秒（8 小时）、在线查询窗口定为 31 天，但代码与部署默认值仍是 30 分钟 / 12 小时 / 90 天，四处（Java 默认值、`application.yml`、`.env.example`、实际下发的 `ClientConfig`）互相之间也不一致。另外“数据留存 12 个月”是留存口径，与“在线查询窗口 31 天”是两个不同的数，不能混用。

### 改法

- `SessionProperties` 默认值 15 分钟 / 8 小时，注释指向 `provisional-policy.json` 的两个秒值；`application.yml` 的 `xx.session.idle-ttl` / `absolute-ttl` 同步为 `15m` / `8h`；`.env.example` 的示例值同步。
- 新增 `V4__policy_parameters_20261019.sql`：只把 `core.config_item` 的 `client-config.value` 里 `maxOnlineWindowDays` 由 90 改为 31、`value.version` 由 `'1'` 升为 `'2'`，并 `config_version + 1`。**不改 V2**——V2 已在部署库执行过，改它会 `checksum mismatch` 直接起不来；用 `WHERE value->>'maxOnlineWindowDays' IS DISTINCT FROM '31'` 保证重复执行是空操作，用 `CASE` 保留运维自定义过的版本号。
- 断言同步：`ClientConfigScalarsTests`（90→31）、`verify-client-config.ps1`（`-eq 31`，并把 `config_version` 断言从“等于 1”改为“≥1 的正计数”，因为 V4 会把它推到 2）、`verify-login.ps1`（`Max-Age=28800`、`now + 15m`、`now + 8h`）。
- 文档：`apps/api/README.md` 的登录示例、TTL 说明、迁移目录树、V2/V4 说明、§8.5 空库链路、§8.7 规矩第 4 条（数据类修正也走增量）全部对齐。
