## 补充记录：2026-10-26 迁移校验脚本加固（DEV-01，评审 A05）

评审 `PR审查报告_20261026.md` 的 A05：`verify-migration-parity.ps1` 用两个**固定库名** `parity_mig` / `parity_ref`，开场一条 `DROP DATABASE IF EXISTS` 再重建，结束的 `finally` 也按固定名删——只要同一实例上有人（或另一次并发运行）也叫这两个名字，脚本就会把人家的库删掉。校验脚本自身不该具备删库能力。

### 改法

- 库名改为**每次运行唯一**：`parity_<pid>_<MMddHHmmss>_mig` / `…_ref`，工作目录 `apps/api/target/pg-parity/<pid>_<MMddHHmmss>` 同源，并发运行互不干扰；`-RunTag <1-24 位 a-z0-9_>` 可把 tag 固定下来（仅用于自测与复现，名字仍带 `parity_` 前缀）。
- 建库前先查 `pg_database`：**名字已存在就拒绝运行、退出码 2**，不做任何 DROP。
- 用 `$createdDbs` 记录本次真正建成的库，`finally` 只删这个清单里的条目 → 中途失败（例如第 2 个库没建成、迁移报错）也只清理自己建的那几个，别人的库与半成品一律不动。
- 保留原有的 0 一致 / 1 漂移 / 2 环境问题退出码语义，以及 `-Keep` 保留工作目录。

## 补充记录：2026-10-26 数据范围改为「元组并集」（DEV-01，评审 A01）

评审 `PR审查报告_20261026.md` 的 A01（P0）：`/me` 的 `dataScope` 原先用三条扁平查询（`bool_or` 标志、场所并集、类型并集）
拼出范围，语义是"类型集合 × 场所集合"。角色甲授 `PLATE@A`、角色乙授 `FACE@B` 时，摊平后变成
`{PLATE,FACE} × {A,B}`，任何"类型 ∈ 集合 && 场所 ∈ 集合"的判定都会放行 `PLATE@B` 与 `FACE@A` —— 凭空多出两条授权（交叉扩权）。
另一半错误在反方向：`auth.user_scope` 被当成"只许收窄"的限制（与角色取交集），而契约
`provisional-policy.json` 的 `userScopeMode` 写的是 `additive_union_of_typed_scope_tuples`，即账号附加授权应当**加法**合并。

### 改法

- `infra/RbacRepository` 删掉 `bool_or` 聚合与三条扁平查询，改为按角色分组的 `SELECT_ROLE_SCOPES` / `SELECT_ROLE_SITE_ALL` /
  `SELECT_ROLE_DATA_TYPE_ALL`，返回 `RoleScope` / `RoleSite` / `RoleDataType`（都带 `role_id`）。扁平鉴权的入口不存在了。

## 补充记录：2026-10-26 登录改为单账号单会话（DEV-01，评审 A02）

评审 `PR审查报告_20261026.md` 的 A02（P0）：`SessionService.begin` 只撤销客户端**呈递上来的那个 SID**。
同一浏览器重复登录没问题，但另一台设备/另一个浏览器首次登录时**没有 SID 可呈递**，旧会话就一直有效——
同一个人可以同时握着多条活会话，与契约 `SessionData` 的"单账号 1 会话，新登录撤销旧会话"直接冲突。
评审同时指出不能用进程内锁来补：多实例部署时它互不可见。

### 改法

- `infra/UserAccountRepository` 新增 `lockById(UUID)`：`SELECT … FROM auth.app_user WHERE id = ? AND deleted = false FOR UPDATE`，
  javadoc 写明"为什么锁这一行""为什么锁里要再判状态"。
- `infra/UserSessionRepository` 新增 `revokeAllForUser(UUID)`：`UPDATE auth.user_session SET revoked_at = now() WHERE user_id = ? AND revoked_at IS NULL`。
- `service/SessionService#begin` 顺序改为：**锁账号行 → 复核 `status='ACTIVE'` → 撤销呈递的旧 SID → 撤销该账号全部其他会话 → 插入新会话 → 绑定 CSRF**，
  全在原有 `@Transactional` 内。保留 `revokeBySidHash(presentedSid)` 是因为共用终端上换账号登录时，呈递的 SID 属于**另一个**账号，
  `revokeAllForUser(userId)` 覆盖不到它。
- 锁里发现账号不可用（停用/软删）时抛 `ApiException(AUTH_INVALID_CREDENTIALS, LoginService.FAILURE_MESSAGE)`，
  与登录失败**同一错误码同一文案**；为此把 `LoginService.FAILURE_MESSAGE` 由 `private` 改为包私有并写注释说明原因。
  不复用 `AUTH_SESSION_EXPIRED`：这条路径没有会话可过期，且改文案等于泄露"账号存在但被停用"。
- 测试：新增 `SessionServiceBeginTests`（5 条，记录型桩断言调用顺序——无 SID 也必须 `revokeAllForUser` 且发生在 `insert` 之前；
  停用/软删账号 401 且不插入；TTL 取自 `xx.session` 配置）；新增 `apps/api/scripts/verify-session-singleton.ps1`（13 条）。
- 文档：`apps/api/README.md` 登录章节新增「单账号单会话：登录必须锁住账号行（A02）」小节，模块表、验证表、目录树、排错表、回归清单同步。

## 补充记录：2026-10-27 审计缺口的补齐（DEV-01，评审复验）
