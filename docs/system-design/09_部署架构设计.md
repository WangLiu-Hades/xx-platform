# 部署架构设计

## 首版拓扑

每套环境部署 Web 静态资源/反向代理、Spring Boot API、Python Worker、PostgreSQL/PostGIS、受控文件卷和日志/指标采集。反向代理统一 TLS 和同源 Cookie；API 不直接暴露数据库/Worker；Worker 仅能访问必要表、文件与外部适配端口。生产优先独立持久卷与备份目标。图见 `diagrams/deployment.mmd`。

| 环境 | 运行边界 | 数据与监控 | 发布门禁 |
| --- | --- | --- | --- |
| DEV | 本地 Compose，Mock 设备/短信/底图，脱敏样例 | 独立开发库与文件卷，日志/指标端点 | 单测、OpenAPI/迁移校验 |
| TEST | 独立 Compose 或等价隔离栈 | 合成/脱敏数据、环境专属指标标签 | API/集成/E2E/故障测试 |
| UAT | 尽量接近生产的拓扑与许可 | 经批准的验收数据；备份恢复演练 | 业务、安全、性能签认 |
| PROD | 按 Q-002 确定主机数、HA 和网络分区；初版 Compose 草案 | 受控生产数据、监控告警、备份 | 变更审批、灰度/回滚、上线观察 |

四套环境配置、凭据、数据库、文件卷与日志均隔离；监控可集中管理，但要按环境独立标记和授权。机密配置由部署环境注入，不写入镜像或仓库。迁移顺序为备份→兼容性迁移→滚动替换/短维护窗口→健康检查→业务冒烟→回滚判定。含不可逆数据迁移的发布须先设计向前修复，不能假定镜像回退就恢复数据。

## Compose 与升级条件

Compose 满足少量固定主机及四人团队的当前实现成本。若要求自动跨机调度、无单点故障、频繁弹性扩容或多租户隔离，则在明确运维人员与监控能力后评估 Kubernetes；升级前先解决 PostgreSQL HA、共享对象存储和会话共享，不能只搬容器。

首版单机文件卷用于导入文件、图片与导出报表，`file_asset` 保留逻辑存储键。跨机部署或容量/备份要求超出单卷能力时换 S3 兼容对象存储并做迁移。数据库、文件卷、应用配置、密钥恢复流程必须联合演练。地图底图与短信/邮件的联网或离线部署由 ISSUE-010/Q-005 决定。

## 数据库发布约束

PostgreSQL14+与PostGIS配套构建共同固定镜像/软件版本；PG14不能使用PostGIS3.0.x。本次验证14.24/3.6.1，仅隔离目录临时库。schema.sql适用于空库，如需升级旧版43表业务库，按database/migration-plan.md另行开发和验证增量迁移；本目录未证明存在该生产旧库；并发索引构建需独立于DDL事务块。数据库owner/应用/Worker账号隔离、连接时区UTC、空间扩展由迁移owner安装；上线前完成实际角色授权、数据与文件恢复、目标版本DDL与容量门禁。
