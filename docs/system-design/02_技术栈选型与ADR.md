# 技术栈选型与 ADR

## 决策方法

源资料中的框架、中间件和 S5 技术栈均是候选。以稳定性、当前需求适配、开发与运维成本为主，性能与扩展能力结合 A-001 的规模情景评估。下表的性能判断是架构推断，不是已压测结果。

| 决策 | 候选与主要取舍 | 首版选择 | 未选原因 / 升级信号 |
| --- | --- | --- | --- |
| 架构 | 普通单体简单但长任务隔离弱；模块化单体保持共享契约；微服务故障隔离更强但治理成本高；混合方案增加一进程 | 模块化单体 API + Python Worker | 15 个微服务增加部署、调用和数据同步；单体内跑重分析影响在线。独立扩容需求出现后再拆特定热点。 |
| 后端 | Spring Boot 的 CRUD/RBAC/事务生态适合主业务；Go 部署轻但团队领域实现与治理需另建；FastAPI 适合算法/ETL 但主后台重复职责风险大 | Spring Boot API；Python Worker 只做数据/分析 | 不选双主后端；若团队实际语言能力不同，需重评开发成本。 |
| 前端 | Vue/React 均可；Vue 组件化与表单/后台页面实现较直接；React 生态广 | Vue 3 + TypeScript + Vite + Element Plus + Pinia + Axios + ECharts | 不建立两套前端栈。人员已有熟练度未见资料，作为 A-008 待验证。 |
| GIS | OpenLayers 适于 2D 图层、选择与绘制；MapLibre 适于矢量底图与样式；Cesium 偏 3D | OpenLayers + GeoJSON；底图经适配器 | 源需求以 2D 为主，无 3D 需求。底图许可与离线可用性需 ISSUE-010 确认。 |
| 主库 | PostgreSQL/PostGIS 同时承载事务、空间、条件查询；MySQL 主库另配空间/分析方案会扩大组件数 | PostgreSQL + PostGIS | 以分区/索引/聚合先验证，1 亿级与复杂搜索按压测触发独立引擎。 |
| 搜索 | PostgreSQL 组合索引和精确检索；OpenSearch 全文/复杂搜索强但增同步链路 | PostgreSQL | 首版没有明确全文相关度需求；检索 P95/索引膨胀不达标再引入。 |
| 分析 | PostgreSQL 聚合/Worker 足以起步；ClickHouse/Doris 提升列式扫描但添同步与运维 | PostgreSQL + Python Worker | 大规模宽表聚合超过预算再以事实表异步投递到独立分析库。 |
| 任务消息 | DB 队列原子性和恢复简单；Redis Queue/ RabbitMQ/Kafka 提升吞吐/扇出但增加运行件 | PostgreSQL `async_task` + 租约 | 告警延迟/积压达阈值且 DB 队列压测失败，再按事件语义引入 MQ。 |
| 部署 | Compose 适于少量节点；Kubernetes 能调度多节点但学习与运维成本高 | Docker Compose + 独立环境配置 | 多节点自动调度、频繁弹性伸缩或高可用要求且运维能力具备再评估 K8s。 |
| API | REST 易生成契约/缓存/审计；GraphQL 灵活取数但权限与查询复杂度治理更难 | REST `/api/v1` + OpenAPI | 页面数据的固定查询/任务模式无需 GraphQL。 |
| 认证 | 有状态服务端会话便于立即失效；JWT 自包含适合多服务但撤销复杂 | 服务端会话 + HttpOnly Secure Cookie | 多端/跨域部署约束确认后再细化，见 ADR-007。 |

### 七维技术决策矩阵

以下“低/中/高”是对**当前四类角色、未知规模**的相对工程判断，不是产品性能测量。成本/学习/运维列越低越省；性能/稳定/适配/扩展列越高越有利。性能评价只表示方案的潜力，实际容量由 07 的压测决定。

| 类别与候选 | 开发成本 | 性能潜力 | 稳定性 | 学习成本 | 运维成本 | 当前适配 | 扩展性 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 架构：普通单体 | 低 | 中 | 中，重任务影响 API | 低 | 低 | 中 | 中 | 不选，隔离不足 |
| 架构：模块化单体+Worker | 中 | 高，重任务独立 | 高，可恢复任务 | 中 | 中 | 高 | 中高 | **选** |
| 架构：微服务 | 高 | 高 | 高，但链路复杂 | 高 | 高 | 低 | 高 | 延后 |
| 后端：Spring Boot 主 API | 中 | 高 | 高，事务/治理成熟 | 中 | 中 | 高 | 高 | **选** |
| 后端：Go 主 API | 中高 | 高 | 中高，取决于自建治理 | 中 | 低 | 中 | 高 | 未选 |
| 后端：FastAPI 主 API | 中 | 中高 | 中，需重复治理 | 低 | 中 | 中 | 中 | 只用 Python Worker |
| 前端：Vue 3 | 低中 | 高 | 高 | 中 | 低 | 高 | 高 | **选** |
| 前端：React | 中 | 高 | 高 | 中 | 低 | 高 | 高 | 未选，避免双栈 |
| GIS：OpenLayers | 中 | 高 | 高 | 中 | 低 | 高 | 高 | **选** |
| GIS：MapLibre | 中 | 高 | 高 | 中 | 低 | 中高 | 高 | 未选，偏底图样式优势 |
| GIS：Cesium | 高 | 高，偏 3D | 高 | 高 | 中 | 低 | 高 | 无 3D 证据 |
| 主库：PostgreSQL/PostGIS | 中 | 高，时空/事务 | 高 | 中 | 中 | 高 | 高 | **选** |
| 主库：MySQL 加空间方案 | 中高 | 中高 | 高 | 中 | 中高 | 中 | 高 | 会增加空间方案复杂度 |
| 搜索：PostgreSQL 索引 | 低 | 中高 | 高，少同步 | 低 | 低 | 高 | 中 | **选** |
| 搜索：OpenSearch | 高 | 高，复杂搜索 | 中，需同步 | 高 | 高 | 中 | 高 | 压测触发 |
| 分析：PostgreSQL+Worker | 低中 | 中高 | 高，少同步 | 中 | 低中 | 高 | 中 | **选** |
| 分析：ClickHouse/Doris | 高 | 高，列式聚合 | 中，需同步 | 高 | 高 | 中 | 高 | 压测触发 |
| 消息：DB Task Queue | 低 | 中 | 高，事务一致 | 低 | 低 | 高 | 中 | **选** |
| 消息：Redis Queue | 中 | 高 | 中，需补持久化语义 | 中 | 中 | 中 | 中高 | 未选 |
| 消息：RabbitMQ/Kafka | 高 | 高 | 高，但治理面大 | 高 | 高 | 低中 | 高 | 吞吐/扇出触发 |
| 部署：Docker Compose | 低 | 中高 | 中，需显式恢复 | 低 | 低 | 高 | 中 | **选** |

## 基础设施裁剪

| 组件 | 当前问题与较简单解法 | 分类与触发 |
| --- | --- | --- |
| PostgreSQL/PostGIS | 统一事务、空间、条件检索、任务表 | 首版必须使用 |
| Docker/Compose | 可复制环境与本地启动 | 首版必须使用 |
| 受控文件卷 + 备份 | 首版单机附件/导出；API 通过 `file_asset` 抽象访问 | 首版必须使用；多机时升级对象存储 |
| Prometheus/Grafana 或现有等价监控 | 采集指标与告警，配合结构化日志 | 建议使用，生产运行前必须有等价能力 |
| Redis | 尚无经测量的热点；先用数据库汇总表和短时进程内只读缓存 | 达到一定规模后使用：多个 API 实例共享热点且 DB P95 超标 |
| MQ/Kafka/RabbitMQ | 当前任务以数据库原子提交、单消费者组和可追踪状态为主 | 达到一定规模后使用：任务积压、扇出或低延时通知无法达标 |
| OpenSearch、ClickHouse/Doris | 增加索引/事实表同步和权限复制 | 达到一定规模后使用：对应检索/聚合压测失败 |
| 独立 API Gateway、配置中心 | 单 API 进程可由反向代理和环境配置处理 | 当前不建议引入 |
| Kubernetes、微服务 | 当前团队/部署规模无证据支持其运维复杂度 | 当前不建议引入 |

进程内缓存仅可用于不敏感、可失效的字典/静态配置；权限与设备状态以权威查询为准。首页采用 `metric_snapshot` 定时汇总，非任意 TTL 缓存。具体键、过期和失效条件见 `07_性能与容量设计.md`。

## ADR 目录

已形成 `adr/ADR-001` 至 `ADR-008`，分别记录架构、后端、数据库、GIS、任务、API、认证与部署的 Context / Decision / Alternatives / Consequences。安全/规模/部署假设变动时，使用新 ADR 修订，不在实现代码中隐式改写决策。

## 数据库版本与存储决策（2026-10-07）

用户指定PostgreSQL14+、PostGIS3.0+；PG14实际需PostGIS3.1.4或更高兼容构建，3.0.x不能搭配14。空间SQL只使用3.0时代已有函数。DB-DESIGN-2采用六schema、公共采集+四payload、typed结果、数据集有效区间版本、独立通知计划/执行和受控文件。额外163表主要为目录/关系/版本，在线查询按域投影而非全表关联；75个显式查询索引之外还包括PK/UNIQUE完整性索引。分区/Redis/专库由真实负载触发，详见ADR-003、03和验证报告。
