# 本地大模型部署与接入

本文件面向交付与运维：把大模型部署在**本机或内网**，让平台智能体通过 OpenAI 兼容接口调用。前端默认地址为 `http://127.0.0.1:11434/v1`，模型默认 `qwen2.5:7b-instruct`，可在页面「模型设置」或 `.env.local` 中修改。

> 结论先说：**推荐 Ollama + qwen2.5:7b-instruct** 做单机演示和验收；内网多人并发再考虑 vLLM。模型未启动、拉取失败或超时都不影响平台业务页面，智能体会自动回退到内置规则引擎。

## 1. 方案对比

| 方案 | 适用场景 | 优点 | 注意 |
| --- | --- | --- | --- |
| Ollama | 单机、少量并发、演示与验收 | 安装简单，一条命令拉模型，自带 OpenAI 兼容 `/v1` | 默认只监听本机；跨端口访问要配 CORS |
| vLLM | 内网多人并发、GPU 服务器 | 吞吐高、可批处理、可做鉴权 | 部署复杂，需要 CUDA 环境和模型权重 |
| LM Studio | Windows 桌面演示 | 图形界面，内置 OpenAI 兼容服务 | 需要开机保持应用运行 |
| Xinference | 多模型统一管理 | 支持多种模型和推理后端 | 资源占用和配置更重 |

前端不绑定厂商，只要服务实现 `GET /v1/models` 与 `POST /v1/chat/completions`（`stream: true` 返回 SSE）即可。

## 2. 模型选型与硬件

| 模型 | 参数量 | 量化后显存/内存 | 适用 | 说明 |
| --- | --- | --- | --- | --- |
| qwen2.5:3b-instruct | 3B | 约 2.5 GB | 低配演示、笔记本核显 | 速度最快，回答质量一般 |
| **qwen2.5:7b-instruct** | 7B | 约 4.7 GB | **推荐：单机验收、日常演示** | 中文和指令跟随较稳，8 GB 显存可跑 |
| qwen2.5:14b-instruct | 14B | 约 9 GB | 有 16 GB 显存，要求更好表达 | 首 token 更慢，建议 GPU |
| qwen2.5:32b-instruct | 32B | 约 20 GB | 24 GB 显存以上 | 质量更好，部署成本高 |
| deepseek-r1:7b / 8b | 7–8B | 约 5 GB | 需要推理过程展示 | 思考链更长，首 token 延迟明显 |

经验值：7B 模型在 RTX 3060 12GB 上生成速度约 25–45 token/s；纯 CPU（16 核）约 4–10 token/s。智能体回答限制在 160 字以内，7B 已足够；**不建议**为了"大"而选择远超硬件的模型，加载失败比模型小更影响演示。

## 3. 安装 Ollama（推荐）

### Windows

1. 从 Ollama 官网下载安装包并安装（需要管理员权限）。
2. 打开 PowerShell 验证：

```powershell
ollama --version
```

3. 拉取并试跑模型：

```powershell
ollama pull qwen2.5:7b-instruct
ollama run qwen2.5:7b-instruct "用一句话说明什么是布控"
```

4. 启动服务（安装后通常自动常驻；没有则手动）：

```powershell
ollama serve
```

### Linux

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5:7b-instruct
systemctl status ollama
```

### 验证 OpenAI 兼容接口

```powershell
curl http://127.0.0.1:11434/v1/models
curl http://127.0.0.1:11434/v1/chat/completions `
  -H "Content-Type: application/json" `
  -d '{"model":"qwen2.5:7b-instruct","stream":false,"messages":[{"role":"user","content":"你好"}]}'
```

`/v1/models` 返回 `data[].id` 即模型名，填入前端「模型名称」。

## 4. 前端接入

### 4.1 默认配置

`.env.local`（已被 `.gitignore` 排除，仅本机生效）：

```ini
VITE_LLM_ENABLED=true
VITE_LLM_BASE_URL=http://127.0.0.1:11434/v1
VITE_LLM_MODEL=qwen2.5:7b-instruct
# VITE_LLM_API_KEY=
```

只填到端口也可以，前端会自动补 `/v1`。修改后需要重启 Vite。

### 4.2 页面设置（推荐现场调整）

右上「模型设置」可修改并**立即测试**：服务地址、模型名称、API Key、温度、超时。保存在浏览器 localStorage（键 `vue-agent-llm-config-v1`），只影响当前浏览器。

- 关闭「启用本地模型」：完全使用规则引擎，不产生任何模型请求。
- 「测试并刷新」会拉取 `/v1/models` 并显示延迟；若配置的模型不在列表中会提示"请确认已拉取"。
- 非本机/内网地址（公网域名）会显示黄色警告，需部署方确认后才应使用。

### 4.3 CORS（跨端口访问必看）

前端在 `http://127.0.0.1:5180`，模型在 `:11434`，属于跨源请求。Ollama 默认允许 localhost 来源；若被拒绝，在**启动 Ollama 的同一个终端**设置后重启：

```powershell
$env:OLLAMA_ORIGINS='http://127.0.0.1:5180'
ollama serve
```

Linux：

```bash
OLLAMA_ORIGINS=http://127.0.0.1:5180 ollama serve
# 或 systemd：Environment="OLLAMA_ORIGINS=http://127.0.0.1:5180"
```

多个来源用逗号分隔；生产环境不要用 `*` 长期放开。

### 4.4 内网服务器部署

模型跑在内网 GPU 服务器时，把前端地址改为服务器内网 IP：

```
VITE_LLM_BASE_URL=http://192.168.10.20:11434/v1
```

同时：

- 只在内网网卡监听：`OLLAMA_HOST=0.0.0.0:11434`（默认仅 127.0.0.1，需显式放开）。
- 用防火墙限制来源网段，不要暴露到公网。
- 如需统一入口，在 Nginx 增加同源反向代理（示例）：

```nginx
location /llm/ {
    proxy_pass http://127.0.0.1:11434/;
    proxy_http_version 1.1;
    proxy_buffering off;                 # SSE 必须关闭缓冲
    proxy_read_timeout 300s;
    add_header X-Accel-Buffering no;
}
```

前端地址填 `http://<平台域名>/llm/v1`。注意反向代理要允许 `POST`、`OPTIONS` 和 `Content-Type: application/json`。

### 4.5 并发与超时

| 变量 | 建议 | 说明 |
| --- | --- | --- |
| `OLLAMA_NUM_PARALLEL` | 2–4 | 同时处理的请求数，显存不足会排队 |
| `OLLAMA_MAX_LOADED_MODELS` | 1 | 单模型更省显存 |
| `OLLAMA_KEEP_ALIVE` | `30m` | 避免每次冷加载 |
| 前端超时 | 60 秒（默认） | 设置页可调 10–300 秒 |

## 5. 没有模型时：本地模型桩

用于演示流式对话链路，不包含真实权重：

```powershell
cd apps/web
npm run llm            # 127.0.0.1:11434；被占用时自动换 11435/11436
npm run llm:selfcheck  # 自检 6 项：模型列表、SSE、[DONE]、语义、非流式、CORS
```

若端口被真实 Ollama 占用，桩会打印实际端口；把该地址填入「模型设置」即可。**模型桩不能作为模型效果验收依据。**

## 6. 安全与数据边界

- 默认只允许本机/内网地址；公网地址仅提示警告，不自动放行数据。
- 发给模型的只有：能力目录、识别到的条件（用户自己输入的目标/时间）、聚合数量（记录数、任务数、告警数等）。不发送采集明细、人员信息、身份证、手机号。
- 会话、模型配置存本机浏览器，不写平台数据库；导出对话为 Markdown，由用户主动触发。
- 模型输出只用于文字解释；页面跳转和业务提交由前端动作目录和用户点击完成，模型无法直接调用后端。
- 建议在模型服务侧保留请求日志（仅记录请求时间/模型/耗时，不记录正文），按内网日志留存制度执行。

## 7. 故障排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 页面显示"本地模型未连接" | 服务未启动、端口不对、地址少了 `/v1` | `curl http://127.0.0.1:11434/v1/models`；设置页重新测试 |
| 浏览器控制台 CORS 报错 | `OLLAMA_ORIGINS` 未包含前端来源 | 设置 `OLLAMA_ORIGINS` 后重启 Ollama |
| 返回 404 / model not found | 模型名与已拉取模型不一致 | `ollama list` 对照；设置页刷新模型列表 |
| 有回复但很慢 | 纯 CPU 推理、模型过大、显存不足 | 换 7B/3B，或使用 GPU；检查是否在 swap |
| 回复为空后自动变成规则应答 | 模型未返回内容/名称错误 | 看设置页连接状态与服务端日志；确认模型支持 chat |
| 首字延迟后中断 | 超时或代理缓冲 | 提高超时；Nginx 关闭 `proxy_buffering` |
| HTTPS 页面调用 HTTP 模型 | 混合内容被浏览器拦截 | 模型服务也走 HTTPS，或同源反向代理 |
| 局域网其他电脑打不开模型 | `OLLAMA_HOST` 仍为 127.0.0.1 | 设置 `OLLAMA_HOST=0.0.0.0:11434` 并放通防火墙 |

## 8. 验收清单

1. `ollama list` 能看到目标模型；`/v1/models` 返回同名模型。
2. 页面「模型设置」显示"连接正常"，延迟可接受。
3. 输入"布控"：有流式回答，回答下方三张操作卡片，来源标签为"本地模型"。
4. 断开模型（停止 `ollama serve`）后刷新：不报页面错误，回答改为"规则引擎"，三张卡片仍可用。
5. 点击"新建布控"能进入综合布控并打开新增表单；点击"查看布控预警结果"进入告警结果。
6. 输入"检索 460000000000001 最近24小时"能把目标与时间带入围栏检索。
7. 记录首 token 延迟与生成速度，作为本机部署的验收数据；模型桩结果不计入。

## 9. 与平台后端的关系

当前对话编排在前端，平台后端契约（`contracts/api/openapi.yaml`）没有智能体会话接口。若后续要求：

- 统一提示词和后端编排：新增会话/消息/意图接口，前端改为调用后端，本地模型仍可部署在内网。
- 对话审计与留存：需要明确留存期限、脱敏规则和访问权限，不能直接复用本机 localStorage。
- 多用户与权限：前端动作已按菜单权限校验，但模型调用本身不做业务授权；真实执行仍由后端逐请求校验。

以上均属于后续接口和部署评审范围，本轮不声称已完成。
